## Context

See proposal.md for the motivation and scope. 当前服务使用单个 SQLite 状态库，schema 为 v3；`jobs` 已有通用幂等键、租约、run token、重试和恢复字段，但现有文章采集 worker 只领取 `capture_article`。现有会话回复 `outbox` 强制绑定入站 Turn 和原始飞书消息，后续每日摘要的主动通知不属于本变更。

现有 `serve-feishu` 已经提供常驻循环、优雅停止和单进程边界。Feed 摄取需要加入同一生命周期，但所有网络和解析工作必须在 SQLite 事务之外完成，避免长事务阻塞会话收件、回复投递和文章采集。

## Goals / Non-Goals

**Goals:**

- 让单用户可以用本地 YAML 配置多个 RSS/Atom 来源。
- 持久化来源状态、HTTP 缓存标记、基线和新增条目，支持重启恢复。
- 用受控 HTTP 和 XML 解析处理公开 Feed，并保留安全、可操作的错误类别。
- 将每次轮询纳入现有 Job 的幂等、租约和重试模型。
- 让后续摘要变更可以读取稳定的 `candidate` 条目和 canonical URL。
- 在没有 Feed 配置时保持当前服务行为和部署兼容。

**Non-Goals:**

- 每日摘要、模型排序、文章正文批量抓取和飞书主动发送。
- 通过飞书消息或管理页面创建、修改和删除订阅。
- 需要 Cookie、HTTP Basic、OAuth 或其他认证的 Feed。
- 将 Feed 全文归档到 Markdown 或把不同来源合并成单一文章实体。
- 引入独立数据库、Redis、外部 scheduler 服务或多进程协调。

## Decisions

### 使用本地 YAML + 启动时校验

Feed 地址、标签和优先级属于本地单用户配置，使用 YAML 保持可读性；使用结构化校验在启动时一次性拒绝错误配置。配置通过环境变量指定路径，Compose 以只读方式挂载文件。运行时不热加载，避免轮询过程中配置变更与基线状态产生竞态；修改后重启即可生效。

未选择仅使用环境变量，因为多个 Feed、标签和来源优先级会变得难以维护；未选择飞书管理，因为那会同时引入命令解析、权限、审计和配置事务，不属于摄取底座。

### 使用 `rss-parser` 归一化 RSS/Atom，保留受控 HTTP

HTTP 请求由应用自己执行，以便统一控制超时、响应大小、重定向和目标地址检查；解析器只接收已通过边界检查的 XML 字符串。`rss-parser` 覆盖 RSS 与 Atom 常见结构，并允许读取自定义字段；解析结果随后转换为项目自己的小型条目模型，避免把第三方对象直接写入 SQLite。

默认响应上限为 2 MiB，单次请求上限为 20 秒；这些值进入配置校验和测试，不向 Feed 服务器暴露原始异常。条目正文不会写入状态库，Feed 摘要只保存受限长度的元数据，后续摘要阶段再决定是否抓取正文。

### Feed 状态与条目使用独立表，轮询意图继续使用通用 Job

schema v4 新增：

- `feed_sources`：显式 ID、URL、启用状态、优先级、标签、ETag、Last-Modified、基线时间、最近检查时间、最近成功时间和安全错误码。
- `feed_items`：Feed 来源、身份键、canonical URL、标题、摘要、作者、发布时间、首次发现时间、状态和最后错误码；`(feed_id, identity_key)` 唯一。

轮询执行仍写入现有 `jobs`，kind 为 `feed_poll`，幂等键为 `feed_poll:<feedId>:<slot>`。这样可复用租约和恢复，但需要给 Job 领取增加 kind 过滤和对应索引；不能让通用无过滤的 `claimJob()` 被两个 worker 竞争使用。

没有把条目状态塞进 Job payload/result，因为 Job 表达一次执行意图，不能替代长期的 Feed 游标、基线和文章去重实体。

### 首次成功检查建立基线，后续条目进入 candidate

轮询在事务外完成请求和解析，在短事务内完成来源游标与条目写入。首次完整成功响应（包括空列表）才设置 `baseline_at`；当次条目状态为 `baseline`。之后出现的新身份写为 `candidate`，已存在身份只更新允许变化的展示元数据，不重置 `first_seen_at`。

身份键优先使用 Feed 的稳定 ID 或 GUID，其次使用规范化 URL，最后使用来源 ID、URL、标题和发布时间组成的稳定哈希。canonical URL 单独保存，作为后续摘要阶段的跨 Feed 合并依据；本阶段不删除重复来源记录。

### 用 Croner 触发“检查到期”，用 SQLite Job 保证可靠性

Croner 负责按照 IANA 时区计算下一次触发时间，启用防重入；定时回调只调用“为到期来源创建幂等 Job”的短操作，不执行网络请求。服务启动时和每次 scheduler tick 都检查缺失或已到期的时间槽，以覆盖服务停机期间错过的轮询。

Feed worker 作为 `serve-feishu` 的独立循环运行：恢复过期 `feed_poll` Job、领取一个当前到期 Job、执行外部请求、提交短事务结果，然后继续处理。服务停止后 scheduler 和 worker 都停止创建/领取；正在进行的请求遵循本阶段的超时和资源清理规则，租约由下次启动恢复。

### Feed 错误只影响来源，不阻塞其他功能

单个 Feed 的失败更新其来源错误和下一次可重试时间，不能让聊天、文章采集或其他 Feed 停止。配置错误和 URL 安全错误是终态；超时、429、5xx、网络不可用和临时解析资源错误可以退避重试。成功的部分条目可以提交，但整体 XML 无法可信解析时不更新成功游标或基线。

日志只写 Feed ID、阶段、状态码类别、尝试次数和退避时间，不写 Feed 正文、完整认证 URL、模型内容或密钥。

## Risks / Trade-offs

- **Feed 格式差异** → 只承诺 RSS 2.0 和 Atom 的常见结构；自定义字段通过归一化适配，无法识别的条目跳过并记录计数。
- **Feed 服务器时间和条目顺序不稳定** → 去重使用稳定身份，候选发现使用 `first_seen_at`；`published_at` 只作为元数据供后续排序。
- **Feed 体积或请求耗时过大** → 固定响应上限、超时和手动重定向检查；失败只退避该来源。
- **多个 worker 误领取不同 kind 的 Job** → `feed_poll` 领取查询必须带 kind 条件和索引，并用混合队列测试证明文章采集 Job 不变。
- **schema v4 与旧版本回滚不兼容** → 部署前备份 SQLite；旧程序看到 v4 会按未来版本拒绝启动，回滚必须恢复 v3 数据库备份，而不是让旧程序直接打开新库。
- **停机期间错过多个时间槽** → 启动时按当前时间和来源状态补建缺失的幂等检查 Job；不补发历史通知，因为本阶段没有通知行为。
- **配置文件含敏感 Feed URL** → 禁止 URL 用户信息，配置文件只读挂载且不写日志；带认证的 Feed 延后到独立设计。

## Migration Plan

1. 备份现有 schema v3 数据库，确认 `integrity_check` 通过。
2. 发布支持 schema v4 的程序；首次打开时以单事务创建 Feed 表和索引，保留全部旧表及记录。
3. 部署只读 YAML 配置；无配置时只验证兼容启动，不启用 Feed worker。
4. 有配置时启动 scheduler，先完成一次基线验证，再观察连续轮询、重启恢复和混合 Job 队列。
5. 回滚时先停止新程序并保留 v4 数据库，再恢复部署前的 v3 备份和旧程序；不让旧程序直接打开 v4 状态库。
