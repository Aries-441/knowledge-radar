# ADR-0004：使用隔离的 Docker 服务部署

- 状态：Proposed
- 日期：2026-09-07

## 背景

项目需要长期运行，并访问飞书、模型、知识库和不可信网页。直接在 Windows 主机运行虽然简单，但依赖安装、进程重启和文件权限都由宿主环境承担。用户希望通过 Docker 统一管理并缩小 Agent 的权限范围。

浏览器是特殊风险边界：它保存可冒用账号的 Cookie，并解析来自互联网的复杂、不可信内容。如果和应用核心运行在同一容器，它会同时接触模型密钥、飞书密钥和知识库写权限，扩大单点失陷后的影响范围。

## 决定

使用 Docker Compose 作为正式部署入口，并拆分两个运行时安全域：

1. `radar` 容器运行模块化单体，包括飞书、调度、任务、pi 和归档。
2. 可选的 `browser` 容器运行 Playwright/Chromium，只保存 Browser Profiles 和提取网页。
3. 人工登录通过按需启动的 `browser-login` 辅助服务完成。
4. 两个常驻服务都以非 root、只读根文件系统和最小 capabilities 运行。
5. 只把知识库的 `Private/Inbox` 挂载给 `radar`，不挂载整个知识库。
6. 不挂载 Docker Socket，不使用 `privileged` 和宿主网络。
7. 匿名或低权限阅读账号可以共用默认 Profile volume；高价值账号必须按信任级别拆分独立的浏览器服务、Profile volume 和内部令牌。
8. 手机远程登录作为显式 Compose overlay 提供：登录服务可以空闲常驻，由受身份保护的出站隧道访问；它不能因此获得业务密钥或 Docker Socket。

浏览器服务暴露窄的内部内容提取接口，不把通用 Playwright/CDP 控制能力暴露给 Agent。

## 结果

好处：

- 宿主机不需要安装项目运行时和浏览器依赖。
- Compose 统一处理启动、停止、健康检查和失败重启。
- 浏览器漏洞无法直接读取模型密钥和知识库。
- Agent 或应用漏洞默认只能修改 Inbox，不能修改博客 Public 内容。
- Windows、Linux 和 NAS 可以共享相同部署模型。

代价：

- 多一个浏览器服务和内部协议需要维护。
- Windows Docker Desktop 下人工登录比直接打开宿主 Chrome 更复杂。
- named volume 的查看、备份和恢复需要专门命令。
- 容器仍共享宿主内核，不能被视为虚拟机级隔离。
- Docker Desktop 本身成为需要持续运行和更新的基础依赖。

## 未选择方案

**所有能力放进一个容器**：部署文件较少，但浏览器同时获得 Cookie、业务密钥和知识库权限，安全边界过大。

**容器直接控制宿主 Chrome**：登录体验较好，但需要向容器暴露宿主调试端口或浏览器扩展通道，边界复杂且容易误用日常 Profile。

**完全在 Windows 主机运行**：调试简单，但依赖、进程和权限隔离不符合正式部署目标。

**Kubernetes**：当前是单用户单机应用，没有集群调度需求。

## 重新评估条件

- 登录态浏览器在 Docker Desktop 中长期不稳定。
- 浏览器服务的维护成本超过其安全收益。
- 项目迁移到已有的受控浏览器平台。
- 需要多用户租户隔离，现有单机 Compose 边界不再足够。
