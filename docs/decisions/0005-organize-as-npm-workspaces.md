# ADR-0005：使用 npm workspaces 组织单仓库

- 状态：Proposed
- 日期：2026-09-07

## 背景

项目包含两个不同安全域：拥有飞书、模型和知识库权限的 `radar`，以及拥有浏览器登录态的 `browser`。它们需要独立依赖和镜像，又共享一份小型的内部通信协议。如果全部代码放在一个 package，浏览器镜像容易携带不需要的依赖；如果拆成多个仓库，版本协调和本地开发成本又不适合个人项目。

## 决定

1. 使用一个 Git 仓库和根级 npm workspaces。
2. `apps/radar` 和 `apps/browser` 是两个可独立构建的私有 package。
3. `browser` 与 `browser-login` 复用 `apps/browser` 和同一镜像，通过不同 entrypoint 启动。
4. 仅建立 `packages/browser-contracts` 共享跨容器协议，不建立通用 `common` 包。
5. 应用内部按业务模块和基础设施适配器划分，业务模块不能导入具体适配器。
6. 根目录只保留仓库级配置、Compose 入口、文档和跨应用测试。
7. 运行数据、实际配置、secrets 和 Browser Profiles 永远位于仓库之外。

## 结果

好处：

- 两个镜像可以只安装各自需要的依赖，安全边界更容易审查。
- 一个根 lockfile 保持跨应用依赖版本一致。
- 内部协议可以同时进行编译期和运行时校验。
- 不需要额外引入 Turborepo、Nx 或 pnpm workspace 工具链。
- 贡献者可以从文件路径直接判断代码所有权和部署位置。

代价：

- 根构建脚本需要正确处理 workspace 顺序和缓存。
- TypeScript 项目引用、容器构建上下文和测试配置比单 package 略复杂。
- 共享协议发生破坏性变更时，两个应用必须协调升级。
- npm workspaces 不负责高级任务编排；如果未来构建规模显著增长，可能需要额外工具。

## 未选择方案

**单 package、单 `src/`**：文件最少，但模糊两个镜像的依赖边界。

**多个 Git 仓库**：运行时隔离更直观，但版本、CI 和本地联调成本过高。

**每个业务模块一个 package**：当前模块只在 `radar` 内使用，抽包不会带来复用价值。

**Turborepo 或 Nx**：当前只有两个应用和一个协议包，没有足够的构建规模证明额外工具链合理。

## 重新评估条件

- workspace 数量或 CI 时间增长到 npm scripts 难以管理。
- 浏览器服务需要独立发布节奏或由其他团队维护。
- 出现第二个真实消费者，需要把某个内部模块发布为稳定 SDK。
- 项目转为多用户服务，现有单仓库权限和发布流程不再足够。
